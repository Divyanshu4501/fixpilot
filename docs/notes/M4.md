# M4 — Harness core + baseline

**Result:** baseline (`gpt-6-luna`, effort `medium`, bash + submit) resolved **14/20 = 70%** of the dev set (95% Wilson CI **48–85%**). Cost: **$0.0036/task**, $0.0051/resolved, $0.071 for the whole run. Median 11.5 steps, 75 s per task. 0 infra failures, 0 empty patches, 100% of patches applied.

## What was built

| File | What it does |
|---|---|
| `fixpilot/tasks.py` | Loads tasks with **only** the 5 visible fields; picks the fixed dev/test sets |
| `fixpilot/images.py` | Pulls images (with retries), removes only the ones a run pulled, estimates download size |
| `fixpilot/score.py` | Runs the official harness and saves a small status per task to `results/<run>/instances.jsonl` |
| `fixpilot/run.py` | The CLI: batches → pull → agents in parallel → predictions → score → cleanup; resumable |
| `fixpilot/analyze.py` | Resolve rate + Wilson CI, costs, steps, failure categories, ablation table |
| `tests/` | 52 unit tests with a fake OpenAI client and a fake sandbox, plus 1 Docker integration test |
| `data/dev_ids.txt`, `data/test_ids.txt`, `data/split_info.json` | The fixed task sets |

## How a run flows

```
data/dev_ids.txt ─► tasks.load_tasks (visible fields only)
                      │
   for each batch of 5 tasks:
     images.ensure_image ── pull (retry ×3) ──► skip the task if it still fails
     ThreadPoolExecutor(4): Sandbox ─► run_agent ─► runs/<run>/trajectories/<id>.json
     write_predictions ─► runs/<run>/predictions.jsonl
     score.score_ids ─► official harness ─► results/<run>/instances.jsonl
     remove pulled images (unless --keep-images)
                      │
analyze.py ─► results/<run>/summary.{md,json}, results/ablation.md
```

## Key ideas, in plain words

- **Allowlist, not blocklist (leakage).** `visible_task` copies the 5 allowed fields and nothing else. A blocklist ("remove `patch`, `test_patch`, …") would leak any field nobody thought of. Verified has a `difficulty` field that isn't on CLAUDE.md's list. `run_agent` also refuses a task with extra fields, as a second line of defence.
- **Leakage test with planted secrets.** The test puts `SECRET_GOLD_PATCH`, `SECRET_FAIL_TO_PASS` etc. into every hidden field, runs the agent against a fake model, and checks that none of these strings appear in anything sent to the model or the sandbox.
- **Largest-remainder method** (how many tasks each repo gets): give each repo `floor(n × share)`, then hand the leftover slots to the repos with the largest fractions. The counts always add up to exactly n.
- **Seeded shuffle.** `random.Random(20261023)` gives the same "random" order every time. The IDs are sorted first, so the dataset's row order can't change the result.
- **Fake client / fake sandbox.** Tests swap in small objects that behave like the OpenAI client and the Docker sandbox, with scripted replies. Tests run in 4 s, cost $0, and need no Docker, which CI (M8) also won't have.
- **Mutation check.** To prove a test can fail, I broke the code on purpose (removed the leakage guard; trimmed output wrongly) and confirmed the right tests failed. Then I restored it.
- **Resumable.** A trajectory file means "done". Rerun the same command and finished tasks are skipped, while `error` tasks are retried. `meta.json` locks the settings: resuming with a different config is refused.
- **Atomic write.** Write to `file.tmp`, then `os.replace` it onto the real name. A crash leaves the old file or the new file, never half a file.
- **Wilson confidence interval.** With only 20 tasks the true resolve rate is uncertain. The 95% Wilson interval is the range that likely contains it. It's used instead of the textbook `p ± 1.96·√(p(1−p)/n)` because that formula breaks for small n (it can go below 0% or collapse to zero width at 0/20).
- **Honest denominator.** Resolve rate = resolved / all planned tasks. Crashes and limit hits count as failures.

## What surprised me / went wrong

- **A network drop crashed the first smoke run.** docker-py's `images.pull()` does **not** raise when a download breaks; it returns quietly, and you get a confusing `No such image` later. Fix: read the pull's progress stream and raise on `{"error": ...}`, retry 3×, and skip a task whose image still won't come (a resume retries it).
- **The same crash leaked a 4 GB image**, because pulling happened before the `try/finally` cleanup. Moved the pulls inside it.
- **My progress output looked frozen.** I piped the run through `grep -v`, and `grep` buffers its output when writing to a file. The run was fine. Lesson: don't filter a long run's output through a pipe without `--line-buffered`.
- **Compressed ≠ on disk.** The 11099 image is a 1.15 GB download but 4.19 GB on disk (~3.6×).
- **The dev set has no task above "15 min – 1 hour"** (by chance, ~15% likely). Not re-drawn (D9). Expect dev rates to be a bit higher than test.
- `load_dotenv()` searches from the *calling file's* folder, not the current directory. A script in the scratchpad didn't find the repo's `.env`.
- **My D2 claim was wrong:** `include=["reasoning.encrypted_content"]` is a legacy no-op with `store=False`. Docs plus a probe confirmed it; the flag was removed.

**Failures (all `wrong_fix`):** django-13401, xarray-7229, pylint-4661, sphinx-9658, sympy-13974, sympy-15976. In every case, 0 PASS_TO_PASS tests broke: the agent didn't damage anything, it just didn't make the right behaviour change.

**pylint-4661 is a special case.** The hidden test does `import appdirs`. The gold fix adds `appdirs` as a dependency (`setup.cfg`), and the evaluation installs it. The image doesn't ship `appdirs` and the sandbox has no network, so the agent couldn't discover that this library was expected. I scored the gold patch on this task (`gold-check-pylint-4661`): **resolved**, so the harness and image are fine. The result stays *unresolved* (only the harness decides). For failure analysis it belongs in "the test requires one specific implementation choice", not "the agent was careless".

**astropy-14598 resolved despite hitting the 30-step limit.** The patch is taken even after a limit, and that partial work passed. This is why D-"patch taken even after a limit" exists.

## What this means for M5

- **Noise:** the CI is 37 points wide. One task = 5 points. An upgrade has to gain ~3+ tasks before it's even suggestive. **Run-to-run variance is real:** astropy-14598 failed in `smoke-2` and passed in `baseline` with the identical config. Since a dev run costs only ~$0.07, running each configuration **3 times** (and reporting mean ± spread) would make the ablation much more trustworthy, for ~$0.20 per row.
- **Testing is already happening:** the agent ran the repo's tests in 19/20 tasks (6/6 failures included). So "test feedback before submit" probably adds little. The failures are semantic: wrong behaviour, nothing broken. Better candidates: a reviewer agent, best-of-N with selection, higher reasoning effort (failed tasks used somewhat more reasoning tokens: a sign they were harder, not a reason by itself), or a stronger reproduce-first rule.
- **Headroom:** 70% on a dev set with no tasks above 1 h leaves only 6 tasks to win. Expect the test set (5 harder tasks) to come in lower.
